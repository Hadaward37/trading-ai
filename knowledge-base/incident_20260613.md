# Incidente — Incubação Sistema 1 nunca coletou dados B3

**Data do diagnóstico:** 2026-06-13
**Diagnóstico por:** Opus 4.8 (achado inicial) + verificação local no código (Fable 5)
**Severidade:** CRÍTICA — invalida a premissa da incubação
**Status:** aguardando decisão de rota (ver fim do documento)

---

## Resumo executivo

A incubação iniciada em 22/05/2026 **nunca esteve viva para os ativos B3**. Durante os
~23 dias decorridos, o scheduler rodou todo ciclo (a cada 15 min), mas produziu
**HOLD puro** em VALE3, PETR4, ITUB4, BBDC4 e IBOV — zero sinais acionáveis, zero
paper trades, zero linhas gravadas em `signals_1h`. **Não existe dataset de incubação.**

A decisão "esperar até 06/07 para analisar o experimento" perdeu o objeto: não há
experimento vivo para esperar.

---

## Evidências

### 1. Persistência de sinal está hardcoded para EUR/USD
`core/scheduler.py:179-182`:
```python
# Only save DB records for the default asset to avoid schema complexity
if symbol == config.SYMBOL:          # config.SYMBOL == "EURUSD=X"
    save_ohlcv(...)
    save_signals(...)
```
- `config.SYMBOL = "EURUSD=X"` (`config.py:30`)
- `config.ASSETS` (`config.py:36-42`) contém **apenas** VALE3/PETR4/ITUB4/BBDC4/IBOV
- O loop principal itera só sobre `ASSETS` (`scheduler.py:357`)
- Logo `symbol == config.SYMBOL` **nunca é verdadeiro** → `save_signals()` nunca executa
- A tabela `signals_1h` congelou em **2026-05-21 23:00** (último dado EUR/USD), exatamente
  quando EUR/USD saiu do universo. Confirmado no backup `trading_20260612.db`.
- **`signals_1h` também não tem coluna `symbol`** — não comporta multi-ativo sem migração de schema.

### 2. O cérebro de scoring é forex-only
- Modelos em `models/`: `lstm_eurusd_1h.h5`, `xgboost_eurusd.pkl` (+ scalers). **Não existe modelo B3.**
- `config.py:101-102`: LSTM (peso 20) + XGBoost (peso 21) = **41% do `final_score`**
- `config.py:113`: `XGBOOST_REQUIRE_CONSENSUS = True` → cancela o sinal se LSTM e XGBoost discordam
- Modelos treinados em EUR/USD, aplicados a candles B3 com scaler de forex, produzem
  probabilidade ~ruído. Com consenso exigido, quase tudo colapsa para HOLD.

### 3. Log da VM confirma: roda limpo, HOLD sempre, sem crashes
`scheduler.log` (lido read-only em 13/06, ciclos 13:01→14:19):
```
[VALE3] No signal change — skipping
[PETR4] No signal change — skipping
[ITUB4] No signal change — skipping
[BBDC4] No signal change — skipping
[IBOV]  No signal change — skipping
```
Grep por `error|exception|traceback|failed` retornou **apenas** linhas `skipping`.
Não há crash — o scheduler está saudável. O problema é silencioso: HOLD perpétuo.

### 4. Backup noturno nunca funcionou
- Crontab: `0 3 * * * cp ...signals.jsonl... 2>/dev/null`
- O pipeline atual grava em SQLite, não em `signals.jsonl`. O `cp` copia um arquivo
  inexistente há semanas, com o erro engolido por `2>/dev/null`. "Backup de nada."

### 5. Threshold — discrepância resolvida (bug 2.3 da revisão Fable 5)
- Runtime real: `config.py:161` → `SIGNAL_CONFIDENCE_THRESHOLD = 55` (escala 0-100, sobre `final_score`)
- Os "0.65 / 0.55" dos docs eram de uma escala antiga (0-1), nunca usados em runtime,
  sem fallback implementado. `edge_thesis.md` corrigido.

## Drift adicional de doc vs. realidade (verificar na decisão)
- `edge_thesis.md` dizia "Timeframe 15min" e "LSTM ausente"; runtime usa `SCHEDULER_TIMEFRAME = "1h"`
  e **ambos** LSTM e XGBoost habilitados (`config.py:105,111`).
- `paper_trades` no backup: última entrada também em **2026-05-21** — nenhum trade novo desde então,
  coerente com HOLD perpétuo nos B3.

## Por que a Rota 1 (patch pontual + reiniciar o relógio) não resolve
Corrigir só a persistência (`scheduler.py:180`) não produz dados, porque **não há sinais
não-HOLD para gravar**. Para a incubação B3 fazer sentido seria preciso:
1. Treinar LSTM + XGBoost para cada ativo B3 (ou um modelo B3 generalista) + novos scalers
2. Migração de schema: `signals_1h` (e `ohlcv_1h`) precisam de coluna `symbol` / tabelas por ativo
3. Remover/ajustar a trava de persistência hardcoded em EUR/USD
4. Revisar `XGBOOST_REQUIRE_CONSENSUS` e os pesos para o universo B3
5. Healthcheck novo: monitor de "linhas novas em signals_1h por dia" (alerta se = 0)

Isso é um projeto de modelagem, não um conserto de bug.

- **Rota A — Reconstruir Sistema 1 para B3:** itens 1-5 acima. Semanas de trabalho.
  Reinicia o relógio de incubação só depois de validar que `signals_1h` cresce com sinais reais.
- **Rota B — Postmortem + pular para Sistema 2:** arquivar v1.0-on-B3, escrever postmortem
  (este documento é a semente), seguir para o Historical Similarity Engine (Pythex).

apenas leitura (incl. SSH read-only) e correção de documentação.
